# 메인 세션의 모듈별 설계 검토

이전 별도 설계 작업은 사용자의 요청으로 중단·보관했다. 그 작업의 초안은 보존하되, 이 디렉터리의 독립 평가를 통과한 것으로 간주하지 않는다. 실제 원본을 구현한 메인 세션이 설계의 통합·수정을 맡고 작성자와 다른 평가자가 재검토한다.

## 평가 단위와 점수의 의미

`../../decomposition/ui-modules.json`과 `core-modules.json`의 모듈 및 `acceptanceQuestions`가 평가 모집단이다. UI의 실제 페이지 7개와 화면에 표시되는 진행 단계 4개는 서로 구분한다. 한 파일을 한 모듈로 간주하지 않고 책임과 사용자 동작을 기준으로 분해한다. 활성 컴포넌트·핵심 처리 경로가 모집단에서 빠졌는지도 별도로 검사한다.

- **명확성:** 원래 소스를 보지 않은 평가자가 해당 질문에 대해 문서만으로 하나의 구현 계약을 결정할 수 있는지 평가한다. 통과 질문 수 / 필수 질문 수 × 100. 근거 없는 pass, 빈 답, 미검토는 통과가 아니다.
- **정확성:** 별도 평가자가 문서의 같은 계약을 고정 원본 코드·타입·테스트와 대조한다. 원본의 실제 동작과 추가 구현 목표를 구분해야 한다. 근거가 확인된 질문 수 / 필수 질문 수 × 100.
- **미해결 모호성:** 평가자의 구체적인 미해결 질문과 fail/unverified 항목. 서로 다른 구현을 허용하는 문장, 누락 상태, 충돌하는 숫자, 실행 불가능한 검증 조건을 포함한다.

**100점 / 미해결 0건은 정의된 모집단과 검토 시점에 대한 결과다.** 알려지지 않은 모든 상황의 완벽성이나 생성 모델의 같은 코드 출력을 보장하지 않는다. 점수 목표에 맞추려고 질문을 삭제·축소하거나 원본의 한계를 숨기면 안 된다. 평가 모집단 변경은 별도 이유와 영향 목록을 남긴다.

## 실제 반복 절차

1. 현재 소스와 초안의 출처를 고정하고 모듈·페이지·API·의존 라이브러리·검증 질문을 목록화한다.
2. 설계 작성자가 각 질문에 답하는 문서/스키마/예시/화면/테스트 계약을 작성한다.
3. **명확성 평가자는 architecture만 읽는다.** 원본 소스를 읽어 빈칸을 스스로 메우면 실패다. 불분명한 구현 선택 두 가지와 필요한 결정을 함께 제시한다.
4. **정확성 평가자는 원본과 비교한다.** 구체적 문서 절과 소스 근거, 차이가 결과에 미치는 영향을 남긴다.
5. 메인 작성자가 피드백을 해결한다. 지적을 삭제하지 않고 수정 위치와 결정을 기록한다.
6. 독립 평가자가 수정된 파일을 다시 읽고 해결 여부를 판정한다. 이전 hash의 평가를 새 파일의 통과로 재사용하지 않는다.
7. 모든 필수 질문을 검토하고 미해결 사항이 없을 때에만 해당 모듈을 인수한다. 최소 두 차례 검토 기록을 남긴다. 평가 결과가 아직 없으면 점수는 **미평가**다.

## 피드백 형식

각 피드백에는 `id`, `moduleId`, `severity`, `document/section`, `problem`, `alternativeInterpretations`, `requiredDecision`, `resolution`, `recheckedBy`를 기록한다. critical/high만 고치고 나머지를 숨기지 않는다. 의도적으로 허용하는 선택이라면 허용 범위와 결과 동등성 검증을 명시하고 평가자가 승인한다.

평가 JSON은 다음 구조를 사용한다. 질문 ID는 모듈 목록과 정확히 일치해야 한다.

```json
{
  "schemaVersion": 1,
  "round": 1,
  "role": "clarity",
  "reviewerId": "independent-agent-id",
  "modules": [{
    "moduleId": "UI-01",
    "checks": [{
      "id": "UI-01-C01",
      "status": "fail",
      "reason": "취소 뒤 어느 페이지로 돌아가는지 두 해석이 가능하다.",
      "evidence": [{"path": "specs/04-ui-motion.md", "section": "해당 상태 전이 절"}]
    }]
  }],
  "issues": [{"id": "R1-UI-001", "moduleId": "UI-01", "severity": "high", "status": "open", "problem": "취소 복귀 상태 미지정"}],
  "inputs": [{"path": "specs/04-ui-motion.md", "sha256": "실제로 읽은 문서의 해시"}]
}
```

`role`은 clarity 또는 accuracy, `status`는 pass/fail/unverified다. 명확성 evidence 경로는 architecture 내부 상대 경로, 정확성의 원본 증거는 `source:` 접두사와 프로젝트 상대 경로를 쓴다. 평가를 마친 사람이 `node architecture/reviews/main-session/score.mjs seal REVIEW.json`으로 입력 해시를 기록하고 `... score REVIEW.json ...`으로 모집단 전체 점수를 계산한다. seal은 의미 검토를 대신하지 않는다.

## 완료 증거의 분리

설계 점수와 패키지 이식성 검사, 원본 테스트, 새 프로젝트 구현 acceptance는 별개다. 원본 테스트 통과나 검증기 자체 테스트로 새 앱이 완성됐다고 표시하지 않는다. 재구현 작업은 PLAN/GOAL의 실제 실행 gate를 별도로 통과해야 한다.

[에이전트 사용 기록](agent-usage.md)은 역할별 인원과 회차별 신규·재사용을 구분한다. 평가 책임자와 보조 평가자를 별도로 설명하며, 집계 마감 이후 호출과 이전 보관 작업은 수치에 섞지 않는다.
